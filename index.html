SRE INCIDENT POST-MORTEM

Anatomy of a $2.8M DNS Blackout in Tier-1 E-Commerce

Published by Reliability Architecture Team • Root Cause Analysis & Production Hardening Guide

1. Incident Summary

During peak holiday readiness testing, ApexCommerce suffered a total global resolution blackout lasting 167 minutes. Despite origin compute (Kubernetes pods, AWS ALBs, Amazon RDS Aurora) operating with 0% dropped packets and 1.2% CPU utilization, over 4.2 million active shoppers were greeted with ERR_NAME_NOT_RESOLVED.

Key Financial Damage:
  • Direct Lost GMV: $2,899,120 (167 minutes @ average $17,360/minute)
  • Wasted Ad Spend: $142,500 on active Google/Meta ads landing on unresolvable URLs
  • Customer Support Inundation: 18,400 tickets and automated shopping bot disconnects

2. The Three Cascading Failure Planes

Plane 1: The Single-Provider Anycast Fallacy

ApexCommerce relied exclusively on a single Anycast authoritative DNS vendor. While Anycast provides physical network resilience against DDoS attacks on individual points-of-presence, all 300+ edge nodes shared a single software control plane. When a corrupted zone signing script was deployed, every nameserver on Earth invalidated signatures concurrently.

Plane 2: The "TTL Trap"

To enable rapid multi-region failover, SREs configured record TTL to 60 seconds. When the authoritative nameservers crashed, recursive resolvers around the world purged their cache within 1 minute. Had records been configured with an emergency TTL buffer or had resolvers implemented RFC 8767 (Serving Stale Data), 80%+ of user traffic would have continued flowing uninterrupted.

Plane 3: The Internal CoreDNS "Thundering Herd"

Outside DNS failure leaked into the internal Kubernetes cluster. When backend checkout pods attempted to resolve the external payment gateway (api.globalpay.net), lookups failed. Aggressive, un-jittered retries flooded Kubernetes CoreDNS pods, pushing CoreDNS CPU to 100% and breaking internal service discovery (cart-service.default.svc.cluster.local).

3. Production Hardening: The 5-Pillar Architecture

1. Multi-Provider Anycast DNS

Delegate 2 NS records to Provider A (AWS Route 53) and 2 NS records to Provider B (Cloudflare). Synchronize records using GitOps via OctoDNS.

2. RFC 8767 Stale Cache Serving

Configure resolvers and clients to return stale cached records when authoritative nameservers return SERVFAIL or timeout.

3. Kubernetes NodeLocal DNSCache

Deploy node-local caching DaemonSets to intercept pod lookups, preventing CoreDNS query amplification storms.

4. Multi-Region Synthetic Probing

Continuously validate RRSIG expiration and authoritative response times from 60+ global vantage points.
